# CLAUDE.md

FamilyDB is a family planning chat bot: Python 3.11+, SQLite, a model from Anthropic, OpenAI or Google behind one provider protocol, Telegram and the web page as chat channels, and a web surface for browsing, editing, status and settings. The design is `docs/DESIGN.md`; server setup is `RUNBOOK.md`.

## How to read the rules here

The rules in this file exist so that a change does not quietly cost the family money, break the prompt cache, open a hole, lose a message, or undo a choice the family made on purpose. Each says why, and most are held by a test that names it. They are not a list of what may not be tried: a design the rules did not foresee is welcome, and a rule that stands in the way of a better one is changed in the same pull request, with its reason, rather than worked around. Four kinds are worth telling apart:

- **Invariants**: cost, the cache, security and delivery. A test holds each; the test changes with the rule, never quietly.
- **Design and feel**: how the page looks and is laid out, its wording and structure, which pages there are, how Vera appears and sounds, what the scripts do. These are open. Whoever is working on the app, an AI agent included, may evolve them without asking first, because the creative process has to grow with the application. `docs/STYLE.md` records the look as it stands and why; a change updates it in the same change, and tests that pin today's markup change with it. The floors that do not move: accessibility, the content security policy, escaping, no model call for a page view, and the evals when her character or prompt changes, since those go into every request.
- **The family's decisions** that are not soft (`docs/DESIGN.md` section 16, with the shared location in section 10 and spending in section 14): who may message the bot and who signs in, what leaves the house (such as a shared location going to the model's company), what may be spent, what each role may do. A change to one of those asks them, and says what it would cost or gain.
- **Defaults**: the conventions that keep the code readable (one module per tool group, one repository per table, the page's wording in `web/views.py`). Follow them unless there is a reason not to, and say the reason where the change is.

When a rule and a reason disagree, the reason wins: fix the rule.

## Core principle: token economy

- Paid inference is a limited resource. Prefer local deterministic code; minimize total cost per successful task, including repeated input, output, reasoning, cache charges, tool searches and retries. Measure actual tokens rather than character counts.
- Human replies are terse. Machine-facing messages contain only necessary validated structured fields: no narrative rationale, duplicate records or unnecessary defaults. Preserve essential constraints and provider schema correctness.
- Automatic household memory must use an already-required conversation request to emit compact deltas. Do not add a routine background extraction call, paid memory retrieval, or a follow-up model call solely to acknowledge persistence. No changes means no unnecessary payload.
- Memory storage, deterministic deduplication, expiry, indexing and retrieval run locally. Supply only relevant context under a budget, always including applicable firm requirements. Preserve prompt-cache stability.
- Bound calls, tool iterations, context, output and retries; account for all billable surfaces. Choose the least expensive configured model that meets measured quality requirements: GPT-6 Luna is the default for chat and lookups for that reason.
- A daily spending limit exists and is tested (`agent/spending.py`, checked in the loop before every call): each call's cost is estimated from `agent/providers/prices.py` and stored in `llm_calls`. A model missing from that table is counted dearer than any listed, so add a price when adding a model worth suggesting. It is an estimate, not the bill; do not describe it as more.
- How every model call decides, sees, acts and is trusted is framed in `docs/AI_CALLS.md`: code knows, the model understands and words. A new kind of call answers its five questions before it is on by default (`docs/AI_CALLS.md` says what an experiment behind a setting may leave open).
- The automatic-memory design and acceptance criteria are in `docs/MEMORY.md`. Memory rides on the chat call: the `remember` tool (`tools/memory.py`), whose `reply` ends a turn that only remembered; `familydb/memory.py` chooses what each message is sent, in the uncached current turn, firm ones always; `/memory` shows it and forgets it.
- How the persona is used and configured, what was fixed and what is left, is in `docs/PERSONAS.md`: she changes how things are said, never what is done.

## Commands

- `uv sync` installs everything. `uv run familydb --help` lists commands.
- People install with the one block in `docs/INSTALL.md` step 1: it makes a deploy key, shows where to add it on GitHub, and runs `scripts/bootstrap.sh`, which runs `scripts/install.sh`. The installer asks at most for a domain name, writes `.env`, installs, migrates, puts HTTPS in front (Caddy, at the server's own address when there is no domain, on 443 or the port `WEB_PUBLIC_PORT` names, which `maintain.sh https --port N|random` moves; `scripts/lib/https.sh`), and schedules backups, for Docker or a virtualenv. Every failure says what to do and that running it again carries on (`again_hint`). Configuration the family would change belongs on the page: it goes on the settings page (a line in `store.settings.BEHAVIOUR` and `web/fields.py`), and becomes a setup step (`web/status.setup_progress`, `web/setup.py`) if the bot is not usable without it. The installer only writes such a value when it is given in the environment. A knob only an operator or a developer would turn can stay in `.env` until somebody wants it on the page. `scripts/uninstall.sh --from-zero` removes everything the install put on a server, after two confirmations, for testing it again.
- Tests: `uv run pytest -q` (no network; each provider's SDK is faked in `tests/fakes.py`, and the shared `settings` fixture pins Claude because most scripts are written for its fake).
- Lint and format: `uv run ruff check . && uv run ruff format .`
- Live checks, need `ANTHROPIC_API_KEY`: `FAMILYDB_LIVE=1 uv run pytest -m live` and `uv run familydb debug validate-tools`.
- Behaviour checks against a real model, a few cents a run: `uv run python -m evals` (`--repeat 3`, `--provider` with `--model` or `--level` to compare models, `--persona KEY|none|FILE`, repeated, to compare personas in runs passed and input tokens, `--case NAME --show` to see one). The cases in `evals/cases.py` are the family's own requests, graded by code on what was called, saved and said. Run them before and after changing a prompt, a tool description or a model. A case that stops holding is either a regression to fix or a case that encoded the old behaviour, which is updated, with the reason in the change; a new behaviour is worth a case once it has settled.
- Jobs by hand: `uv run familydb enrich --idea N`, `uv run familydb suggest --window this-weekend [--discover]`, `uv run familydb digest --now`, `uv run familydb follow-ups --now`.
- The web page: `WEB_PASSWORD=test uv run familydb web --port 8099`, then open http://127.0.0.1:8099/ (the home page; `/chat` to talk to it, `/ideas` and `/ideas/new`, `/plans` and `/plans/month`, `/tasks` for things to do and their reminders, `/family` for who the bot talks to, `/status` for what is connected and what it has cost, `/settings` to change anything). The page reads the live Google calendar only through `app.calendar`; with none configured it shows the saved plans and says so.
- What each setting is and where it came from: `uv run familydb config`.
- Inspect a request without sending it: `uv run familydb debug prompt --as Sam "what should we do?"`, or `--kind enrich --idea 57` for a lookup. It is built by the same code that sends it.

## Layout

- `src/familydb/pipeline.py`: one inbound message end to end. Channels call `handle_incoming`. A voice note (`channels.base.VoiceNote`, a way to fetch it) is stored as a mark first (`store.messages.unheard`), then fetched and heard under the message's lease through `gateway.listen`, and its words replace the mark after `store.messages.VOICE_PREFIX`; one that cannot be heard is given up with a `voice_*` line, since the recording is never kept.
- `src/familydb/delivery.py`: message leases (a claim with an expiry, renewed while a turn runs) and at-least-once delivery of stored replies. `calendar_sync.py` brings the bot's plans in line with their Google events. `family.py` holds the rules for adding and changing family members, and for how each signs in to the page. `roles.py` is the three roles (admin, parent, kid) and what each may do. `task_service.py` changes tasks and their reminders in one place, for the tools and the reminder job alike, repeats included: on a schedule from the first reminder or counted from when last done, in the family's wall time (`next_time`), Done recording a time round rather than ending it, and a birthday's reminder listing the gift ideas saved for whoever's it is (`gift_for`, `ideas.gifts_for`). `windows.py` reads a task's preferred window in code, as days and parts of the day from a short list of words, and reads nothing with any other word in it. `agenda.py` reads what is on, from Google or else the saved plans, for the page and the commands. `commands.py` answers Telegram's /today, /week, /tasks and /now by code with no model call (the calendar, the chat's own tasks, the suggestion engine without the web): only the family may ask, the command is stored processed so no turn ever takes it, and the answer is her reply to it, under a heading from `voice.EVENTS` `cmd_*`. `buttons.py` is what goes under a reminder and a follow-up on Telegram and what a tap does: code calling the tool the model would have called, as the member who tapped, after checking the family list and what the button sends back, with no model call; the tap is kept as a message (`TAP_PREFIX`) its tool call belongs to, and is said in her words (`voice.EVENTS` `tap_*`). A message's buttons are stored with it (`messages.buttons`), and go through `App.button_senders` where a channel can show them. `personas/` is the persona layer, who the assistant is: a `Persona` is her name, her label, her character and her lines, one folder each (`default/`, Vera as first written and the default, and `brief/`, a shorter Vera: `persona.toml` names her and labels her, as "{name}, in brief", `character.md`, and `lines.toml`, where a line may be a list of wordings), and `personas.active(settings)` is the one in force (the `persona` setting's, `PLAIN` for `none`, with the family's words from `/settings/personality` laid over hers: `persona_name`, what they call her; their rewrite of her character, kept per persona in `Settings.persona_text` as a `PersonaRewrite` with `of`, hers as it shipped when they wrote it, and laid over her alone; `persona_notes`, their notes on how she talks; and `voice_lines`). Her name is written once, in `persona.toml`, unless the family give her one: her character, her lines and the family's rewrites of them say `{name}` (`Persona.prompt` fills it in for the model, `voice.say` for a line). The prompt, `voice.py`, Telegram's `/start` and contact, and every page (each template's `assistant` and `has_persona`) ask it; nothing else works out who she is from those settings or writes her name. A persona setting written as an older key still finds her (`personas.key_for`, `RENAMED`): a setting that fails to load takes every stored one with it, keys included. Her character, then the family's notes, go first in the chat prefix, ahead of `prompts/system.md`, which says what to do; the job wins where they meet, and the product says so (`agent/prompt.py` `JOB_HEADER`), not her character. Workers never carry it. `whereabouts.py` keeps where a member's phone said they were (a Telegram share, or the web chat's position), named once by the reverse geocoder, for three hours of use and a day at most (the `forget_locations` job deletes it then, whether or not anyone shares again). `voice.py` is the voice layer every unprompted message is routed through: a line may have several wordings, and `say` chooses one by a CRC-32 of the event and its `seed` (the message's own id) or of the facts, never by chance, so a resend says the same words; `reads_as` shows each on the Personality page. `privacy.py` sets the owner-only umask every command runs under and tightens files an older version left readable.
- `src/familydb/agent/providers/`: one module per model vendor behind a small protocol. `base.py` holds the types the loop speaks in; `anthropic.py`, `openai.py` and `gemini.py` translate them, and each can ask its vendor whether a model name exists (`model_exists`, which costs no tokens). `prices.py` is the price table, with no SDK in it, which the spending limit and the settings page's model suggestions both read. `catalog.py`, also SDK-free, is each company's lineup by level (everyday, better, best), with whether each model thinks; everyday is the company's own model setting, its cheapest by default, and `providers.model_at` picks the model for a level, never one cheaper than everyday, which `gateway.KINDS` names per kind (`chat_level`, `digest_level`, `lookup_level`; the retry job asks a failed digest again as the digest, `pipeline.DIGEST_UPDATE`). A model added to the lineup needs a price, and a test holds the catalog to what the provider modules send. Each also hears voice notes where the vendor can (`listener`, `transcribe`: OpenAI's speech-to-text endpoint, Gemini sent the recording; Claude cannot), and `hearers` says who is asked. Adding a vendor means one module and one name in `NAMES`; nothing outside this folder should mention an SDK.
- `src/familydb/agent/`: `gateway.py` is the one door to a model: `KINDS` declares each kind of call (chat, digest, retry, enrich, discover) with its prompt, tools, web budget and limits, and for a worker the `hand_back` tools whose success ends the turn without another call, and `ask` runs one and records it under its kind; `listen` hears a voice note, the one call that is not a turn, limited and recorded the same way. `compose.py` builds each request from labelled parts (instructions, family, ideas, tools, history, message) and records their sizes with every call, so the real input total can be shared out by part. `prompt.py` renders the chat prefix, `history.py` rebuilds the chat, `loop.py` is the manual tool loop, `worker.py` runs the small separate turns that may use the web (enrichment, discovery) with `prompts/enrich.md` and `prompts/discover.md`; `prompts/system.md` is the product spec the chat model follows.
- `src/familydb/tools/`: `registry.py` declares and dispatches tools; one module per tool group. `places.py` is the place cache (`lookup_place`, `check_open`, `save_place`, `skip_place`); `suggest.py` exposes the engine as one `suggest` tool and `report_finds` for the discovery worker; `tasks.py` is `add_task`, `update_task` and `list_tasks`.
- `src/familydb/suggest/`: the suggestion engine as code, one module per stage (`context`, `shortlist`, `evaluate`, `discover`, `compose`, `log`) behind `engine.run`. The model frames the question and writes the reply; the verdicts and reasons come from here and are logged to `suggestions`. Time is minutes, not blocks: each day's free stretches between its bounds (08:00-22:00 unless the question names a part of the day, "now" from this minute), so never reason about morning/afternoon/evening there.
- `src/familydb/store/`: `db.py` (connection, transactions, JSON, migrations), `migrations/*.sql`, one repository module per table returning pydantic records. `logins.py` holds each person's password hash, apart from `members` so a hash never travels with a member record into the prompt. `settings.py` is the one the page writes: `BEHAVIOUR` and `SECRETS` are the whitelist of what may be changed from outside a file.
- `src/familydb/channels/`: message dataclasses, the console channel, the Telegram channel (text and voice notes, `asyncio.to_thread` into the sync pipeline, run by `TelegramSupervisor`, which follows the token setting so a new token needs no restart and keeps the bot's name and description in Telegram in step with the name it goes by and its `start` line, hers or FamilyDB's under none, with no model call) and the web channel (`WebChat` runs a turn on its own thread so the page can answer the form post at once).
- `src/familydb/web/`: the page. `__init__.py` is the Flask factory over an `App`, `auth.py` is the sign-in gate (who is asking, as a `Visitor`; each person with their own password, or the family's shared one until an admin has theirs; only an admin past it to `settings`, `setup` and `family`), the CSRF token and the `refused()` check every form runs, `once.py` makes a form do its work once however often it is sent, `routes.py` the reading views (home, ideas, plans list and month, restaurants, things to do, what she remembers, status), reading what is on through `familydb/agenda.py` (Google, or the saved plans), `status.py` what the status page reads, `chat.py` the chat page and the box Home shares with it (`box`, and `glance` and `standing`, which say how the conversation stands from the log and the channel with no model call), `edits.py` the forms that change an idea, an outcome, a plan or a task (the tick beside a task is `finish_task`), `family.py` the Family page and Your password (`/you`), `settings.py` the settings pages (`/settings`, a card to each part saying how it stands, then a page for each of `fields.SECTIONS`, the Personality page among them, whose forms each say which page they came from so the answer comes back there), `setup.py` the setup pages (`/setup`, one step at a time: you, password, AI model, home, Telegram, family, calendar; progress is read from what is configured, by `status.setup_progress`, never stored), `fields.py` the pages, the groups on each (fine-tuning folded) and the boxes, drawn from `Settings` itself, with the help under each and the words a choice is shown in, `views.py` the wording helpers, `server.py` the waitress lifecycle, plus `templates/` (`_ui.html` holds the shared macros: `icon`, `page_head`, `chip`, `kind_label`, `chat_line` and `waiting_line` for the conversation, `presence` for her screen, `tick`, and `crt` and `radar` for the green screens; `_ask.html` is the box everybody writes to her in, on Home and in the chat; `_settings.html` holds the settings pages' `box`, `group` and `form`; `_company_cards.html` and `_key_steps.html` are shared by setup's model step and the AI model settings page) and `static/` (`style.css`, `ask.js`, the page's one script, `fonts/`, and `icons.svg` and `favicon.svg`, which `scripts/icons.py` builds from a pinned Lucide release and the page's own mark, never edited by hand). How the page looks, and the rules a change to it keeps, are in `docs/STYLE.md`.
- `src/familydb/integrations/`: Google Calendar, Open-Meteo and the geocoder (Nominatim, Open-Meteo fallback) behind small Protocols; tests use the fakes in `tests/fakes.py`.
- `src/familydb/jobs/`: the APScheduler `BackgroundScheduler` and the jobs: retries, `enrich` (worker turn per pending idea), `weekend_digest` (a synthetic question through the pipeline), `follow_ups` (no model call), `plan_checks` (daily at `plan_check_hour`, no model call: the evening before a plan, rain for an outdoor idea or its place listed as closed then gets a heads-up with a backup from the engine; all well, nothing is said), `reminders` (every minute, no model call: queues a due reminder and sends it once; a failed send is the retry job's), `forget_locations` (deletes shared positions past their day, no model call), `nudges` (every 15 minutes, no model call: brings up a task kept for a window `windows.py` can read when it comes round and the calendar is free, each once a week and one a day in a chat; `task_nudges` turns it off), `catch_up` (after a restart) and `settings_watch` (moves the schedule when a setting does). Each job's schedule is described once in `scheduler.job_specs`; jobs open their own connection with `app.connect()` and reply through `app.senders`.

## Rules that keep it working

- The family's own words about themselves (`about_family`, on `/settings/personality`) go in the family context of the cached prefix: they change when someone edits them, not per message.
- Nothing volatile in the cached prompt prefix. Tools, the system prompt, the family context and the idea list must not contain dates, times, the sender, or per-request ids. Those belong in the current user turn (`render_user_turn`).
- Rendering is deterministic: idea lines, JSON (`store.db.to_json`, sorted keys), tool ordering (sorted by name), server tools appended last.
- One SQLite connection per thread. Writes go inside `store.db.transaction`. Tools own their own transactions so partial progress survives a failed turn.
- Migrations are append-only numbered files; never edit one that has been applied. Schema changes to FTS-indexed columns need an FTS rebuild in the migration. The next one is `0026`. A migration that rebuilds a table other tables point at starts with `-- foreign_keys: off`, which `db.migrate` honours around its transaction (SQLite's own procedure; with them on, dropping the old table runs every `ON DELETE` of the tables that point at it), and checks its own work before it commits, as `0018` does. Number `0007` is reserved and never used: a database from an early build may have applied a `0007` that is not in this tree, and must never mistake a new 0007 for it (`tests/test_migrations.py` knows the gap).
- Everything the bot says of its own accord is worded by `voice.say` (the persona's line, the family's rewrite, or the plain one), never a string literal at the call site; a new kind of message is a line in `voice.EVENTS`. A proactive message goes out through `voice.hand_over`, which holds it for a moment when the family is talking so the next reply carries it (the only message marked delivered without its own send, with that reply); the minute job sends what no reply carried. No model call is ever made just to word one.
- A reply is stored before it is sent and marked delivered only after the send succeeds: anything that sends goes through `delivery.deliver`, never straight to a channel's sender. Anything that works on an inbound message holds its `lease`, so a restart leaves nothing stranded and two workers never answer one message.
- Every tool is always declared to the model that may call it, and the list never varies between turns, because a varying list would cost the prompt cache. Availability is checked at dispatch; unavailable tools return `{"available": false, ...}` as a non-error result so the model reports the skipped check instead of retrying. Tools marked `worker_only` are left out of the chat list: they belong to a worker turn and would otherwise cost input tokens on every message.
- Tokens are the running cost. Before adding anything to the cached prefix, or a scheduled job that calls the model, check `familydb debug cost` and keep the idle path free: every job must read the database and return without an API call when there is nothing to do. Code that runs the suggestion engine with no model call (the commands, the evening check) passes `refresh_stale=False`, so it never queues a paid lookup either.
- Tool input models use `Literal` and handler checks instead of numeric or length constraints; strict schemas strip those.
- The core is synchronous. Async adapters (Telegram) call the pipeline through `asyncio.to_thread`; anything that sends from another thread goes through the channel's thread-safe sender.
- Tools reach external services only through `ToolContext.calendar` and `ToolContext.weather`, never by constructing clients themselves, so they stay testable with fakes.
- The loop knows nothing about any vendor. It builds a provider-neutral request and reads back a normalised reply; every request shape, cache marker, response block and error mapping belongs to a provider module. A test asserts the request built for a given message is stable, so check it after touching either provider.
- A turn may move to the other provider only on its first call, before any tool has run, because starting again after a write would repeat it. `worth_switching` decides which failures are worth moving for.
- What an Anthropic request carries depends on the model: adaptive thinking and effort unless it is one of `OLDER_MODELS`, the dynamic-filtering web tools only for `DYNAMIC_WEB_MODELS`, the refusal fallback only for `REFUSAL_FALLBACK_MODELS`. A wrong guess is a 400 on every request, which is how lookups on the default Haiku worker were broken; `tests/test_alpha_regressions.py` pins each case.
- Dispatch refuses a tool that was not declared for the turn, and an enrichment turn may only write to its own idea: fetched pages can talk a model into naming any tool.
- Every model call goes through `agent/gateway.ask`, or `gateway.listen` for hearing a voice note, and `tests/test_gateway.py` fails if anything else starts a turn, sends to a provider or asks one to transcribe. A new kind of call is a line in `gateway.KINDS` that answers the five questions of `docs/AI_CALLS.md`, never a direct `run_turn`. What the answer means stays with the caller.
- The chat agent never gets the web tools. Web access happens only in worker turns (`agent/worker.py`) with their own prompt, a tool subset, `max_uses` and `worker_max_iterations`; results come back through strict client tools (`save_place`/`skip_place`, `report_finds`), never parsed from prose. Fetched pages are information, not instructions.
- No transaction may be open around a worker turn: the nested loop writes its own audit rows. Discovery results live in `App.discover_cache` keyed by window; failures are never cached.
- Before a paid call, `spending.admit` checks the limit and holds the call's estimated cost in `spend_holds`, in one short write transaction; recording the call gives the hold back, and a switch to the fallback provider re-holds at the fallback's price (`spending.adjust`) before it is asked. Nothing is locked while the call is on the network, so a slow lookup never holds up the family's chat, and two processes still cannot spend the same remaining dollars. Every vendor client has a timeout. Budget interruptions must report completed writes without another model call.
- Browser idea revisions are checked inside the tool's write transaction; calendar form identities flow through `ToolContext.operation_id` to the durable calendar operation log. Keep these preconditions out of model tool schemas.
- No module in `web/` reaches a table itself, and each view opens its own connection with `app.connect()` inside a `closing(...)`. Four may cause a write, each through one door: `chat.py` hands a message to the pipeline through `channels/web.py`, `edits.py` dispatches `add_idea`, `update_idea`, `record_outcome`, `create_event`, `update_event`, `delete_event`, `add_task`, `update_task` and `remember` through `app.registry`, `family.py` adds and changes people, and their passwords, through `familydb.family`, and `settings.py` writes `app_settings` through `store.settings` (the behaviour form, the keys form, the company-and-key form that checks a key with its company first, the shared family password for `store.settings.LOCK` while there is one, and the Personality page for `store.settings.PROFILE`) and two files: the session key (`keys.rotate`, signing everyone out) and the Google token (`google_calendar.finish_consent`). Two tests in `tests/test_web.py` hold that by walking the AST and they name what each may call, so anything more is a deliberate line there. Every other module reads and nothing else; the page may use `calendar_sync.event_changes` to read Google but never the sync functions, which write.
- The family list is who the bot talks to, so it is not a tool: the model must never be able to change who may message it, or who signs in. Member changes go through `familydb/family.py`, which keeps a name to one person, always keeps an active admin (and, once people sign in as themselves, an admin who can), and refuses a change made on a form drawn before somebody else saved.
- A form on the page is a tool call, not a second write path. Adding one means asking which tool already does it; if none does, the tool is what to write, because the model should be able to do it too. What the tools cannot do the page cannot do, so when a form needs something no tool offers (unsetting an optional number, say, which `update_idea` cannot do yet because it reads a missing field as "leave it alone"), the tool grows, and the page and the model both get it; the page never gets a write of its own.
- Every form posts with a CSRF token and an Origin check through `auth.refused()`, and flashes its result under a named category (`edit`, `settings`) so two pages' notices never mix. A form that changes something also carries `once_token()` and its view is wrapped in `@once`, so a double click or a resend does the work once. The page is served with `Referrer-Policy: same-origin`: under `no-referrer` a browser posts with `Origin: null` and nobody can sign in, which the test client never shows because it sends no Origin at all. Check forms in a real browser.
- Behind a proxy, the forwarding headers are waitress's business (`web/server.proxy_options`), not Flask's: waitress strips them from any peer it was not told to trust before the app runs, so a Flask middleware sees nothing and every sign-in fails the Origin check. Flask's test client skips waitress entirely, so proxy behaviour is tested through a real server on a thread (`tests/test_web.py`), and was checked through real Caddy and nginx.
- Scripts come only from the page itself: the content security policy is `script-src 'self'`, never `unsafe-inline`, and there is no inline script. Within that, scripts are a design choice like any other: add one when it makes the page better. What must keep working with scripts off is reading, every form and sending a message, so the page stays usable on any browser and the forms keep their CSRF and once-only path. Today there is one, `static/ask.js`, the box's, which does what a browser gives to nothing else: it keeps an unsent message in the tab's session storage as it is typed and puts it back when the box comes back empty (forgotten once the thread shows it arrived, and when the tab closes), fills the box from the ways to start, and sends the phone's position with a message while "Send where I am" is ticked (off until someone ticks it; the server keeps no position without it). The chat page waits for its answer with a `<meta http-equiv="refresh">` that is only emitted while a turn really is running, and never on a page holding words somebody typed, which it would take with them: while a turn runs the box is closed instead, and waiting on the retry job, when the box stays open, the script looks again only while nobody is writing (the meta refresh is in `<noscript>`). Keep styling in `static/style.css`: the policy's `style-src 'self'` allows no inline style. Templates escape by default; never mark anything from an idea, a place or a fetched page as safe.
- A setting can be changed from the page, so nothing may cache one, the Telegram token included (the supervisor re-reads it every few seconds). `App.refresh()` is called at every entry point (each message, each job, each page view, each scheduler tick) and rebuilds `App.settings` when the stored values have moved; read `app.settings` when you need it rather than holding on to it, and if you build something from it, say so in `App._forget_built` so it is built again. Adding a setting to `store.settings.BEHAVIOUR` also means a line in `web/fields.py`, in the group of the page it belongs on, with its help written for the family; tests check that every setting is on exactly one page.
- Where a member is goes in the current user turn (`render_location_line`), never the cached prefix, and only while fresh. The family chose to send it: the chat model and the discovery worker get the place name and coordinates, so nobody has to type where they are.
- Who reads the reply goes in the turn too, never the prefix: in a shared chat (a Telegram group, the page's conversation) `render_audience_line` says everyone there reads it, and whether kids are among them; a private chat gets no line.
- An API key is write-only: stored, never rendered into a form, never written to the change log, and shown only after the password the person signed in with is typed again.
- Setting up is the page's job, not a file's: `/setup` walks a new install through it, and each of its forms is one that already exists, posting to its owner with a `then` that may only name a `/setup` page (`auth.setup_return`). The home page sends there until it can answer (somebody on the list and a model). A new thing that has to be configured is a setup step if the bot is not usable without it.
- Each person signs in as themselves: a name and their own password, stored only as a hash in `member_logins` (`passwords.py`, `store/logins.py`, the rules in `familydb/family.py`). There are three roles, admin, parent and kid, and what each may do is one table of permissions in `familydb/roles.py` (sign in and read, chat, change, manage); kids stand in as parents until they need limits of their own. The page asks `visitor().may(permission)`, never about a role: `auth.NEEDS` says which permission each blueprint needs. An admin gives everybody else a starting password, made up and shown once (held in memory for the page that shows it, never in the session cookie, which is signed but not sealed), and the gate lets that person nowhere but `/you` until they have chosen their own. Changing your own asks for the one in force, unless it was a starting one. Each session carries a mark of the password it was opened with, so a new one, being switched off, made a kid or having it taken away signs that person out everywhere. The chat and the edit forms act as whoever is signed in, never as a name the form sends. `familydb password [NAME]` makes a starting password on the server, for the first admin unless named. Until an admin has their own, the page takes a password the family shares: `WEB_PASSWORD`, the installer's, or one chosen on the settings page (`store.settings.LOCK`); the first admin's own password (`family.claim`) ends it, and the rules never let the last admin who can sign in go, so it never comes back.
- Web wording lives in `web/views.py`, never in `agent/render.py`: that one feeds the cached prompt prefix and must not change for the sake of a page.
- No page view is a model call. Home and the chat read the log and word their own lines (her last line, "Answering a message now.", the ways to start); only a message sent is a call, through the pipeline. `test_browsing_asks_nothing_of_a_model` holds it.
- Vera is the one the family talks to, so the page speaks of her by name (`personas.active(settings).name`, in every template as `assistant`), and nothing else works out her name. How she appears is design, open like the rest of the look: today she is never drawn, and where she appears it is her screen, full of glyphs nobody can read (`presence` in `_ui.html`, drawn by the stylesheet), while the smiling mark is FamilyDB's. `docs/STYLE.md` says why it was chosen (principle 9) and what she has instead ("Her screen"), and the reason is worth weighing before changing it.
- Keep replies short. A change in how she behaves is often cheapest as a line in `prompts/system.md`; when code is the better place for it (anything code can know, per `docs/AI_CALLS.md`), change the code.
- Every pull request is reviewed before it is merged, however much it carries: what slips through lands on the family. Separate concerns in separate commits keep a large one readable.
