# CLAUDE.md

FamilyDB is a family planning chat bot: Python 3.11+, SQLite, a model from Anthropic, OpenAI or Google behind one provider protocol, Telegram and the web page as chat channels, and a web surface for browsing, editing, status and settings. Design: `docs/DESIGN.md`. Server setup: `RUNBOOK.md`, `docs/INSTALL.md`.

## How to read the rules

Rules here exist so a change does not quietly cost money, break the prompt cache, open a hole, lose a message, or undo a choice the family made on purpose. Each says why; many are held by a test. They record what mattered most when they were written and are meant to change as the app does: improving one is part of the work, not a detour from it.

When a rule stands between you and a better design:

- Say so, whatever you then do. Meeting a rule's letter with a worse design and quietly breaking it are the same mistake: each hides a question the owner should see. A PR that changes a rule, or keeps one at a cost, says so in its description, in a line starting `Rules:`.
- Change the rule rather than work around it: in the same PR, the rule, the test that holds it, the documents that repeat it, and the new reason. An exception is a change too, named beside the rule with its reason, as `EXCEPTIONS` in `tests/test_layering.py` does.
- A rule the task runs into is part of the task, so changing it is not widening the PR. One you think wrong elsewhere is a suggestion in the PR or your reply, not part of the diff.
- When a rule and its reason disagree, the reason wins. A reason can also still be true and matter less than it did: weigh it by What matters most, below, and say what the change costs and gains.
- Asked for ideas or a design, give the best ones even where they need a rule changed, saying which and what that costs. The rules keep changes honest; they do not shorten the list before the owner sees it.

How far you go on your own depends on the kind of rule. Under Rules that keep it working an invariant is marked **Invariant** and one of the family's decisions **The family's decision**; an unmarked rule is design and feel or a default. Elsewhere in this file and in `docs/`, a rule about what may be spent (the limits, not how to spend less), what leaves the house, what is kept, who may do or see what, or something lost or done twice is one of those two, marked or not; the rest is design and feel or a default. Layout says where things are and how they work today, not what must stay.

- **Invariants** (cost, cache, security, and nothing lost or done twice): hold the outcome, not the mechanism. What must stay true (every model call checked against the day's limit, nothing volatile in the cached prefix, a reply stored before it is sent) stays until the owner agrees otherwise; how it is kept true today (one door, a module, a list) may be redesigned while a test still holds the outcome. Changing an outcome is proposed with what it costs, never done quietly, and its test changes with it.
- **The family's decisions** (rows marked Family in `docs/DESIGN.md` section 16; shared location section 10; spending section 14): who may message the bot and who signs in, what leaves the house, what is kept, what may be spent, what each role may do and see. Ask before changing one, saying what it costs or gains; a PR alone does not decide it. What holds is what they decided, not how it is built: the code that keeps it may be redesigned like any other.
- **Design and feel** (look, layout, wording, pages, how Vera appears and sounds, what scripts do): open; evolve freely, including by AI agents. `docs/STYLE.md` records the look and why; update it in the same change, and the tests that pin today's markup. Floors that only the owner moves: accessibility, the content security policy, escaping, no model call for a page view, and the evals when her character or prompt changes.
- **Defaults** (the layering, one repository per table, one module per tool group, the page's wording in `web/views.py`): follow unless you see a better way; then take it and say why. A test holding one asks "did you mean to?": answer it by changing the test with the reason, not by bending the code around it.

## What matters most

When choices pull against each other, or a rule against a better idea, weigh them in this order:

1. How it looks and feels to the family.
2. What it costs to run.
3. Nothing lost or done twice.
4. The family's safety and privacy.
5. Code that reads simply to the next person.

The order weighs what is open to choose. It does not trade away an invariant or one of the family's decisions on its own: those change only as above, with the owner or the family agreeing, whatever they cost in feel or money.

## Token economy

- Paid inference is limited. Prefer local deterministic code; minimize total cost per successful task (input, output, reasoning, cache charges, tool searches, retries). Measure tokens, not characters. GPT-6 Luna is the default for chat and lookups for that reason.
- Human replies are terse. Machine-facing messages carry only necessary validated structured fields, with provider schema correctness preserved.
- Memory rides on the chat call: the `remember` tool (`tools/memory.py`) emits compact deltas, and its `reply` ends a turn that only remembered. No routine background extraction call, paid retrieval, or follow-up call to acknowledge persistence. Storage, dedupe, expiry, indexing and retrieval are local; `familydb/memory.py` picks what each message is sent, in the uncached current turn, firm ones always. Design and acceptance: `docs/MEMORY.md`. `/memory` shows and forgets it.
- Bound calls, tool iterations, context, output and retries. Choose the cheapest configured model that meets measured quality.
- The daily spending limit (`agent/spending.py`) is checked before every call (in the loop per call, and in `gateway.listen` for a voice note). Cost is estimated from `agent/providers/prices.py` and stored in `llm_calls`; prices in force are the daily check's (`familydb/model_watch.py`) laid over the built-in table by `prices.use`. A model neither knows is counted dearer than any listed, so add a price when adding a model worth suggesting. It is an estimate, not the bill.
- Every kind of model call decides, sees, acts and is trusted as framed in `docs/AI_CALLS.md` (code knows, the model understands and words). A new kind answers its five questions before it is on by default.
- Recipes, dinner and the grocery list: `docs/RECIPES.md`. Kids' wish lists: `docs/WISHES.md`. Persona (changes how things are said, never what is done): `docs/PERSONAS.md`. Ideas, finds, scouting, suggestions and recommendations, the words and the plan for the back pocket: `docs/FINDS.md`.

## Commands

- `uv sync`; `uv run familydb --help`. Tests: `uv run pytest -q` (on every core, by `pytest-xdist` and `-n auto` in `pyproject.toml`; `-n 0` for one process, as a debugger wants; no network; provider SDKs faked in `tests/fakes.py`; the shared `settings` fixture pins Claude). Lint: `uv run ruff check . && uv run ruff format .`.
- Live (need `ANTHROPIC_API_KEY`): `FAMILYDB_LIVE=1 uv run pytest -m live`, `uv run familydb debug validate-tools`.
- Evals against a real model (cents a run): `uv run python -m evals` (`--repeat 3`, `--provider` with `--model` or `--level`, `--persona KEY|none|FILE`, `--case NAME --show`, `--web` to let lookups search, billed per search). Cases in `evals/cases.py` are the family's own requests, graded by code on what was called, saved and said; a case may seed the household (`seed`), run with no calendar (`calendar=False`), and name work not built yet (`waits_for`), which reports it as a gap rather than a failure until it holds. Run before and after changing a prompt, tool description or model. A case that stops holding is a regression or encoded the old behaviour; update it with the reason.
- Jobs by hand: `familydb happening [--now]` (what is on near home: each source when due, or all with `--now`, the search within its month's budget), `enrich --idea N`, `suggest --window this-weekend [--discover]`, `digest --now`, `follow-ups --now`.
- Web: `WEB_PASSWORD=test uv run familydb web --port 8099` (the family's pages, on one frame: `/` Now, `/about`, `/chat`, `/eat`, `/do`, `/week`, `/kids`, `/soon`, `/lists`, `/did`, `/board` for a kitchen tablet, and a page per place `/idea/N` (also `/place/N`), plan `/plan/N`, reminder `/reminder/N`, day `/week/DATE`, kid `/kids/NAME`, list `/lists/NAME`, happening `/soon/N` and outing `/did/N`; `/api/find` is search in the box; the back office behind the avatar: `/more`, `/memory`, `/status`, `/settings`, `/family`, `/wiki`). Calendar is read only through `app.calendar` (`recent_events`, cached a minute unless the bot wrote); with none configured it shows saved plans.
- Example sites: `uv run python -m examples` writes a made-up household's pages (`examples/household.py`, Friday 16 October 2026, 5:02 pm) as linked static HTML in `example-sites/`, as Sam (admin), Maya (11), the kitchen board and a first day, to walk through before going live; forms say what they would do and send nothing; `--serve PORT` runs the household live. `tests/test_examples.py` keeps it building, so a page change that breaks it shows there.
- `familydb config` shows each setting and its source. `familydb debug prompt --as Sam "..."` (or `--kind enrich --idea 57`) shows a request built by the same code that sends it. `familydb debug cost` for cost.
- Dependabot opens monthly PRs; SDK floors in `pyproject.toml` are the tested versions; raise with `uv lock`.
- Install: the one block in `docs/INSTALL.md` step 1 runs `scripts/bootstrap.sh` then `scripts/install.sh` (asks at most for a domain, writes `.env`, installs, migrates, puts Caddy HTTPS in front on 443 or `WEB_PUBLIC_PORT`, schedules backups; Docker or virtualenv). Every failure says what to do and that rerunning carries on (`again_hint`). `maintain.sh https --port N|random` moves the public port, `maintain.sh port N|random` FamilyDB's own `WEB_PORT`. `scripts/uninstall.sh --from-zero` removes everything after two confirmations. What the scripts print is about this run: what is different from last time (`upgrade_changes`: commits, pull requests, migrations, packages, settings), then a line a step (`step`, `ok`, a redrawing line while a slow one runs), then one last line from `finish` and a `recap` of warnings; no background a person who ran it already knows, and Enter is yes (`approve ... yes`) except for what cannot be undone. A command that ends in `finish bad` exits 1 (`FINISH_BAD`), so what the last line says is what a cron job reads. `maintain.sh check` is two looks in one report: the machine's (`scripts/lib/doctor.sh`, a `dc_*` function a section: files, git, config, python, database file, service, web server, https, host, backups; it reads and never repairs, needs nothing from the program so it still runs when the program will not start, and probes as the service account so "readable" means readable by the service) and `familydb doctor` (`doctor.py`, grouped under `▸ Name`). Both feed `doctor_row` in `common.sh`: a name is reported once and the first word wins (the machine's), a section with nothing wrong folds to a line, `doctor_summary` names the first thing to fix; a new check is a row with the command that fixes it, in whichever looks can see it. `maintain.sh doctor` (`scripts/lib/repair.sh`) is the guided one: it sweeps (`sweep`, shared with `check`), reads the service's log when it is unwell (`dr_read_log`), builds a plan in the order a page comes up (`dr_plan`: `pl_add KIND FUNC TITLE WHY DO`, kinds safe, net, risky, tidy; `need` for what only the person can do), explains it root cause first, does the safe steps on one Enter (`dr_run`, each a `fix_*` that changes one thing and says nothing when it works), sweeps again and reports; a new repair is a `fix_*`, a rule in `dr_plan` and a test, and it never spends a model call or answers a data-losing question by itself. `maintain.sh rescue` (`scripts/lib/rescue.sh`) is break glass: it looks, says what it found, asks before each change and backs the database up first; what loses data asks for a typed yes and ignores `--yes` (`rs_confirm_risky`), and `upgrade` records `last-upgrade` in the ledger so `rescue rollback` works after the upgrade finished. `upgrade` fetches with `GIT_TERMINAL_PROMPT=0` and `--force` for tags, refreshes `origin/HEAD` from the remote (`refresh_default_branch`) and follows the default branch, names a failed fetch for what it is (`fetch_trouble`), refuses before asking while a shipped file is changed on the server, then stops the bot before the code moves (Docker builds the image first, while the old one runs), takes the backup once it is stopped, prints the way back before the checkout, puts everything back and starts the bot again on a failure before the migrations (`upgrade_undo`, through `undo_on_failure`), rewrites the service file only when it is as the installer wrote it (`unit_as_installed`), and from the checkout on is finished by the new code's `maintain.sh` (`upgrade_handoff`, `--resume`, its state in `UPGRADE_*`), so a release can change its own steps. Every `uv sync` goes through `uv_sync` or `uv_vars` in `common.sh`, which keep uv's cache and Python inside the install (a virtualenv rebuilt on a Python under /root cannot be run by the service account; a test holds every call site to it). `.env` is read with `env_value` and written with `env_file_write`, which follow python-dotenv (inline comments, `export`, quotes, the last line wins) and are held to it by `tests/test_env_file.py`. A command that changes the install holds `take_lock`; `approve` with no terminal and no `--yes` is a failure, never a quiet no. `tests/install_fixture.py` builds an install that is well on a temp folder, with stand-ins for systemd, curl, df and the rest, for the tests of both (`test_doctor_machine.py`, `test_rescue.py`). The pieces (`banner`, a title bar like an old DOS window's, `frame_bottom` and its bar, `kv` rows marked `✓ ! ✗`, `show_commands` in cyan, `NO_COLOR`, `FORCE_COLOR`, `FAMILYDB_ASCII`) live in `scripts/lib/common.sh`: use those rather than a bare `echo`, and never colour a pipe. The shell tests cut functions out of `maintain.sh` and run them with `common.sh` sourced, so a function there may call only what `common.sh` has or the test's stubs (`tests/test_script_output.py` holds what a person reads off the screen). Configuration the family would change belongs on the settings page (a line in `store.settings.BEHAVIOUR` and `web/fields.py`), and a setup step (`web/status.setup_progress`, `web/setup.py`) if the bot is unusable without it; the installer writes such a value only when given in the environment. Operator-only knobs may stay in `.env`.

## Layout

- The modules stand in an order, bottom to top, and each imports only from its own level or below (`tests/test_layering.py`; every upward import is named there with its reason, so each is on purpose): `base/` (the kernel: `config.py` the `Settings`, `clock.py`, `dates.py` (dates, times, `fmt_minutes` and `last_hour_passed`, the evening the lookups, judgements and scouting wait for), `errors.py`, `roles.py`, `urls.py` (`clean_url`, for anything a model or a fetched page handed over); imports nothing above it), `personas/`, `integrations/`, `store/`, then the domain modules directly in the package (what the family's things are and how they change: `family.py`, `task_service.py`, `voice.py`, `delivery.py` and the rest), `tools/`, `agent/`, `scouting/`, `suggest/`, then the orchestration modules directly in the package (`test_layering.ORCHESTRATION`: `app.py`, `pipeline.py`, `commands.py`, `buttons.py`, `undo.py`, `picks.py`, `judgement.py`, `model_watch.py`, `usage_watch.py`; `cli.py`, `doctor.py` and `__main__.py` are entry points and may import anything), then `channels/`, `jobs/` and `web/`. A new module directly in the package is domain unless it wires tools, the agent or the engine together, in which case it is added to `ORCHESTRATION`.
- `pipeline.py`: one inbound message end to end; channels call `handle_incoming`. Telegram with `gather_seconds` calls `receive` (store now, held under `delivery.GATHER`) then `answer_gathered` (defers to a newer message from the same person in the same chat, else answers all their waiting messages in one turn and one reply, claimed via `delivery.claim_also` and folded in with `messages.fold_into`). Turns in one chat run one at a time per process (`_one_at_a_time`). A voice note (`channels.base.VoiceNote`) is stored as a mark (`messages.unheard`), heard under the message lease through `gateway.listen`, and its words replace the mark after `VOICE_PREFIX`; unhearable ones are given up with a `voice_*` line (recording never kept). A photo (`PhotoNote`) likewise through `gateway.look` (`prompts/look.md`, `PHOTO_PREFIX`, `photo_*`).
- `delivery.py`: message leases (expiring claims, renewed while a turn runs by the process's one `Renewer` thread, whatever it holds) and at-least-once delivery of stored replies. `calendar_sync.py` aligns plans with their Google events in one request (sync token in `calendar_sync_state`). `agenda.py` reads what is on (Google, else saved plans); `free_time.py` computes event days and free stretches.
- `family.py`: add/change/remove members (birthday → age in code; for kids male/female set by an admin, only age reaching the model; what `remove` takes with it is `store.members.POINTING_AT`, which a test holds to the schema, so a new table pointing at a member must say), each person's own things (push devices; her replies they pinned, `pin`/`unpin`, at most `PINS_MOST`, kept in `pins`, drawn beside the box and atop Chat), sign-in, Telegram linking by one-time admin-made link (`invite`, `accept_invite`, hashed in `telegram_invites`). `base/roles.py`: admin, parent, kid and their permissions. `saved_plans.py`: the plans kept here read as a calendar, the busy time when no Google calendar is connected (plans are made without one, and go on it once one is: `calendar_sync.adopt_local`). `plan_service.py`: what follows a plan, kept in step when it changes (both `update_event` and `calendar_sync.apply_event` call `changed` in the transaction that stored it: a moved plan is checked and asked about again, and a reminder set before it with `remind_before`, a task with `plan_id`, is worked out again from the new start or cancelled with it; it says when the plan is and is done once it is over, `finish_over`, from the reminders job). `task_service.py`: task and reminder changes for tools and the reminder job (repeats on schedule or from last done, in family wall time; birthdays list gift ideas). `wish_service.py`: wish-list rules for tools and page (`docs/WISHES.md`). `windows.py` reads a task's preferred window in code from a short word list, free time (any day with two hours free) and "this weekend", which ends on the Sunday after it was said (`tasks.window_until`). `presents.py`: whom a present (an idea of kind gift; any way of saying present is saved as gift) is kept from: every kid, always, and the grown-up it names unless somebody chose others (`ideas.hidden_from` holds only the grown-ups chosen; NULL is the default); to-dos about it (`tasks.idea_id`) go with it (`visible_tasks`); pages, chat tools and birthday reminders all ask it, and the model's idea record never carries the column.
- `push.py`: Web Push for people who use only the page (RFC 8291 encryption and RFC 8292 signing, written out over `cryptography` and `httpx`): once one of her own messages is delivered on the page (`App.notifiers`, called by `delivery.deliver`, never changing delivered state), the devices of whoever reads that conversation are told "{name} has a message", never the words, on one background thread; a gone device is taken off. Devices are kept in `push_subscriptions` (through `familydb.family`'s `subscribe_push`), the install's key in `push_key`, made at start. `undo.py`: taking back the last change: a write tool leaves its inverse (`registry.keep_undo`) for dispatch to store with the call, and `take_back` puts it back only while the record is as that change left it, once, for whoever made it or may change things (the `undo` tool, `/undo`, the page's Undo, the button under a private reply). `commands.py`: Telegram /today, /week, /tasks, /now, /lookup, /undo, /list, /dinner by code, no model call, and the same questions in plain words as the whole message on any channel (`WORDS`, `in_words`, asked by `pipeline._handle` and `receive` before the turn); family only; stored processed so no turn takes it; the answer is her reply under a `voice.EVENTS` `cmd_*` heading. `buttons.py`: buttons under a reminder (and I'll handle it, `MINE`, on a row of its own under one that is everyone's) or follow-up, a row per thing where a message is about several (`in_row`; a tap takes off its own), and what a tap does: code calling the tool the model would have called, as the member who tapped, after checking the family list; no model call; the tap is kept as a message (`TAP_PREFIX`), said by `voice.EVENTS` `tap_*`; buttons are stored with the message (`messages.buttons`) and go through `App.button_senders`; the page's chat draws a reminder's as forms (`edits.finish_task`, `edits.snooze_task`).
- `happening.py`: what is on near home, for everything but its job: the family's name for it (`NAME`, "What's going down?" today), written once (a test holds that nothing else spells it, so a rename is one line), how each source is named, which calendars the settings call for, and what its model calls cost this month. Its finds are offered by `suggest/listed.py`, listed on `/happening` (a third tab beside Plans' List and Month, for grown-ups), and set on a settings page of its own (proposed calendars as ticks, any other a line, folded into `event_feeds`).
- `meals.py`: recipes (docs/RECIPES.md), all by code: the situations a recipe suits guessed from its facts (`guess_occasions`, kept apart as `occasions_guessed`, a maybe, never the family's), tonight read from the plans that cut it short (`situation`), the family's rest for recipes (`rest_days`, `remember`'s rule with rest_kind recipe), recipes ranked for a meal with reasons (`rank`, `pick`; a fact rules one out, taste only lowers it), and a recipe's facts kept with the family's word standing over a page's (`keep`, `from_page`). `groceries.py`: what to buy read out of an ingredient line by rule (`parse`) and recipes put on a list, shared things once, staples left off, amounts as the thing's note (`put_on`). Recipes are ideas of kind recipe with a row in `recipes` (`store/recipes.py`); the prompt's idea list leaves them out (`ideas.list_for_prompt`), the engine never offers one, and `find_recipes` finds them. A pasted link is read by code (`integrations/recipe_page.py`, the schema.org Recipe block, the calendar reader's address checks) by the `recipe_links` job, and a page with none by the `fill_recipe` worker in the evening's lookups (`scouting/fill.fill_recipe_in`).
- `picks.py`: her picks, made ahead (docs/INTERFACE.md section 3): the `picks` job, hourly between 8 and 22, runs the suggestion engine with no model call (`engine.assess(record=False)`, so nothing is logged as a suggestion) for the family's next free stretch and, from Thursday, the weekend, and keeps each set in `pick_sets` (`store/picks.py`); Now and This week read the current set and never make one (`test_browsing_asks_nothing_of_a_model`). The find tile prefers a recommended find, keeps to its `put_from`/`put_until`, and writes `put_forward_at`, so a find rests a week from other sets unless its day is near (`REST_DAYS`, `NEAR_DAYS`). What could we do? lists recommended finds under New ideas (`finds.recommended`, `find_acts` in `_dest.html`, shared with a find's page). `familydb picks --now` makes a set by hand; the `picks` setting turns the job off.
- `personas/`: a `Persona` is name, label, character and lines, one folder each (`default/` Vera, `brief/`): `persona.toml`, `character.md`, `lines.toml` (a line may be a list of wordings). `personas.active(settings)` is the one in force (`persona` setting; `PLAIN` for `none`; family overlays from `/settings/personality`: `persona_name`, `Settings.persona_text` as `PersonaRewrite` with `of`, `persona_notes`, `voice_lines`). Her name is written once, in `persona.toml`; character, lines and rewrites use `{name}`; the prompt, `voice.py`, Telegram and every page ask `personas.active`, nothing else works out who she is. Old keys still resolve (`personas.key_for`, `RENAMED`). Her character, then the family's notes, go first in the chat prefix, ahead of `prompts/system.md`; the job wins where they meet (`agent/prompt.py` `JOB_HEADER`). Workers never carry it.
- `voice.py`: every unprompted message is worded here. A line may have several wordings; `say` picks by CRC-32 of event and `seed` (message id) or facts, never chance, so a resend says the same words. `audience.py`: who reads a chat (kid's own, group with a kid, shared page), so workings are said plainly where a kid reads (`voice.PLAIN`, `plain=`) and presents listed only where everyone may decide. `routing.py` sends person-only messages (their reminder, nudge, idea note, plan outcome) to them, decided as each goes: from a group, the page or somebody else's chat to their own Telegram chat (`reach`; else, for a kid or one who never wrote, their page conversation, `audience.page_chat`), and a task for everyone to the family's chat (`for_task`, `family_chat_id`); `CONFIRMED` is the ✓ a group's "saved" is. `hours.py`: a place's opening hours as its record keeps them, read for a date and worded (the engine, the evening check and the page ask here; the lookup tools write them). `looks.py`: the looks the page can wear and how a choice is read (`members.look` through `family.choose_look`; the cookie is `web/looks.py`). `whereabouts.py`: where a phone said a member was, named once by reverse geocode, kept 3 hours of use and a day at most (`forget_locations` deletes), then its name is taken out of the reply that said it and the kept model words and results that carried it (`store/place_names.py`, `place_names` table; `members.erase` does it too). `privacy.py`: owner-only umask and tightening of older files. `export.py`: the family's data to take away (plans as a calendar file, ideas and things to do as spreadsheets, everything as JSON for an admin; `familydb export`), never a secret or a way in. `whatsnew.py`: the top section of the shipped CHANGELOG.md, for the Status page's What's new. `health.py`: whether it is well, for `/healthz`, `familydb health` and Docker's HEALTHCHECK: the database answers and a scheduler that should be running has ticked (`store/heartbeat.py`, by the settings watch).
- `agent/providers/`: one module per vendor behind a small protocol (`base.py` types; `anthropic.py`, `openai.py`, `gemini.py`). Each has `model_exists` (free), `listed_models`, maps a 404 for the model to `trouble="model"`, can hear voice (`listener`, `transcribe`; not Claude; `hearers` says who) and look at photos (`viewer`, `describe`; `lookers`). `prices.py` is SDK-free: built-in prices plus the daily check's (`use`, from `App.refresh`), model suggestions (`suggestions`), notes (`note`). Request shape is read from the model name; modules list older generations (`anthropic.OLDER_MODELS`, `gemini.OLDER_MODELS`), not the current one. `catalog.py` (SDK-free) is each company's lineup by level (everyday, better, best) and whether each thinks; `providers.model_at` picks a model per level, never cheaper than everyday; `gateway.KINDS` names per kind `chat_level`, `digest_level`, `lookup_level` (the retry job asks a failed digest again as `pipeline.DIGEST_UPDATE`). A model added to the lineup needs a price; a test holds the catalog to what the modules send. A built-in vendor is one module and one `Company` in `companies.py`, the registry every label, key setting, model prefix and price-list name is read from (nothing keeps its own table of the three; `tests/test_companies.py` holds it to the settings it names). Every company's models are one shape, `config.CompanyModels` (everyday chat, everyday lookup, better, best): the page's `Settings.company_models` by slug, laid by `Company.models` over what the environment says for a built-in one (`config.OLDER_MODELS`, read only into `env_company_models`) or the definition for an added one; a provider's `model_for` asks its company, a form box is `Company.box(field)` and `companies.models_with` turns boxes into what is stored. ## Rules that keep it working

Each kind is as How to read the rules says: an invariant holds its outcome, not today's mechanism; one of the family's decisions is asked about first; an unmarked rule is design and feel or a default.

- **Invariant (cache).** Nothing volatile in the cached prompt prefix: tools, system prompt, family context and idea list contain no dates, times, sender or per-request ids; those go in the current user turn (`render_user_turn`). The family's `about_family` goes in the family context (changes only on edit). Where a member is (`render_location_line`, only while fresh) and who reads the reply (`render_audience_line`: shared chat says everyone there reads it, and whether kids are among them; private chat none) go in the turn too. The family chose to send location: the chat model and discovery worker get place name and coordinates.
- **Invariant (cache).** Rendering is deterministic: idea lines, JSON (`store.db.to_json`, sorted keys), tools sorted by name, server tools last.
- **Invariant (cache, security).** Every tool is always declared to the model that may call it; the list never varies between turns (it would cost the cache). Availability is checked at dispatch; unavailable returns `{"available": false, ...}` as a non-error result so the model reports the skipped check. `worker_only` tools are left out of the chat list. Dispatch refuses a tool not declared for the turn, and an enrichment turn may only write to its own idea, a find's lookup to its own find (`worker_idea_id`, `worker_find_id`; fetched pages can talk a model into naming any tool). Tool input models use `Literal` and handler checks, not numeric or length constraints (strict schemas strip them).
- **Invariant (cost).** Tokens are the running cost: before adding to the cached prefix or a scheduled job that calls the model, check `familydb debug cost`; every job must read the database and return without an API call when idle. Code running the suggestion engine with no model call (commands, evening check) passes `refresh_stale=False`. No page view is a model call: Home and the chat read the log and word their own lines; only a sent message is a call (`test_browsing_asks_nothing_of_a_model`).
- One SQLite connection per thread. Writes inside `store.db.transaction`. Tools own their transactions so partial progress survives a failed turn. No transaction open around a worker turn (its loop writes audit rows). Discovery results live in `App.discover_cache` keyed by window, framing and the brief's steady part, and are kept as `request` finds; failures never cached.
- **Invariant (nothing lost or done twice).** Migrations are append-only numbered files; never edit an applied one (`db.migrate` records each as applied by its checksum in `schema_checksums` and refuses to run on a database whose applied files were changed since, or that is missing one numbered below its newest, `MigrationError`; a database from before checksums is taken on trust once). Schema changes to FTS-indexed columns need an FTS rebuild in the migration. Next is `0065`. A migration rebuilding a table other tables point at starts with `-- foreign_keys: off` (honoured by `db.migrate` around its transaction) and checks its own work before commit, as `0018` does. `0007` is reserved and never used (`tests/test_migrations.py` knows the gap).
- The core is synchronous; async adapters (Telegram) use `asyncio.to_thread`; anything sending from another thread uses the channel's thread-safe sender.
- Tools reach services only through `ToolContext.calendar` and `ToolContext.weather`, so they stay testable with fakes.
- Everything the bot says of its own accord is worded by `voice.say`, never a literal at the call site; a new kind of message is a line in `voice.EVENTS`. A proactive message goes out through `voice.hand_over`, which keeps its kind (`messages.sent_as`; the digest's reply is kept as `digest`), so the Messages page lists each kind (`web/status.automatic`, `views.AUTOMATIC`: a new kind is a line there). It holds a message a moment while the family is talking so the next reply carries it (marked delivered with that reply); the minute job sends what no reply carried. No model call is made to word one. Where a kid reads (`audience.plain`), workings are said as the `voice.PLAIN` line: kids never see how the bot works or why it does not (a family decision, `docs/DESIGN.md` section 16; `tests/test_kids_plain.py`, `test_a_kid_is_never_shown_how_it_works`).
- **Invariant (nothing lost or done twice).** A reply is stored before it is sent and marked delivered only after the send succeeds: anything that sends goes through `delivery.deliver`. Anything working on an inbound message holds its `lease`, so a restart strands nothing and two workers never answer one message; a message waiting to be answered with later ones is held under `GATHER`, which only a turn answering it may take over and which lapses to the retry job.
- A company is named by its slug and asked of `agent/providers/companies.py`, never by a table of three in the file that needs a label, a key's setting or a model's owner. A setting that names one (`provider`, `worker_provider`) may name an added company, so nothing indexes a table by it without the registry.
- The loop knows nothing about any vendor: it builds a provider-neutral request and reads a normalised reply; request shape, cache markers, response blocks and error mapping belong to provider modules. A test asserts the request for a message is stable; check it after touching a provider.
- **Invariant (nothing lost or done twice).** A turn may move to the other provider only on its first call, before any tool has run (restarting after a write would repeat it); `worth_switching` decides which failures qualify.
- Request shape depends on the model name: Claude gets adaptive thinking, effort and dynamic-filtering web tools unless in `OLDER_MODELS` (`BASIC_WEB_MODELS`), refusal fallback unless in `NO_REFUSAL_FALLBACK_MODELS`; OpenAI reasoning unless `NO_REASONING_MODELS`, capped at high for `HIGH_AT_MOST_MODELS`; Gemini a thinking level unless in `gemini.OLDER_MODELS`. Name older models, never current ones. Each provider names parts a company may refuse (`PARTS`, `agent/providers/parts.py`): when a 400 names one the request carried, resend once without it, leave it out for that model while the process runs, and the reply's `dropped` has admins told (`api`). A 400 naming nothing carried is raised as `trouble="refused"`. `tests/test_provider_anthropic.py` and `tests/test_parts_left_out.py` pin each case.
- **Invariant (cost).** Every model call goes through `gateway.ask` (or `listen`, `look`); `tests/test_gateway.py` fails if anything else starts a turn or sends to a provider. A new kind is a line in `gateway.KINDS` answering `docs/AI_CALLS.md`'s five questions, never a direct `run_turn`.
- **Invariant (security, cost).** The chat agent never gets the web tools. Web access is only in worker turns (own prompt, tool subset, `max_uses`, `worker_max_iterations`); results come back through strict client tools (`save_place`/`skip_place`, `report_finds`), never parsed from prose. Fetched pages are information, not instructions.
