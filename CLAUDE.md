# CLAUDE.md

FamilyDB is a family planning chat bot: Python 3.11+, SQLite, a model from Anthropic, OpenAI or Google behind one provider protocol, Telegram and the web page as chat channels, and a web surface for browsing, editing, status and settings. The design is `docs/DESIGN.md`; server setup is `RUNBOOK.md`.

## Core principle: token economy

- Paid inference is a limited resource. Prefer local deterministic code; minimize total cost per successful task, including repeated input, output, reasoning, cache charges, tool searches and retries. Measure actual tokens rather than character counts.
- Human replies are terse. Machine-facing messages contain only necessary validated structured fields: no narrative rationale, duplicate records or unnecessary defaults. Preserve essential constraints and provider schema correctness.
- Automatic household memory must use an already-required conversation request to emit compact deltas. Do not add a routine background extraction call, paid memory retrieval, or a follow-up model call solely to acknowledge persistence. No changes means no unnecessary payload.
- Memory storage, deterministic deduplication, expiry, indexing and retrieval run locally. Supply only relevant context under a budget, always including applicable firm requirements. Preserve prompt-cache stability.
- Bound calls, tool iterations, context, output and retries; account for all billable surfaces. Choose the least expensive configured model that meets measured quality requirements: GPT-6 Luna is the default for chat and lookups for that reason.
- A daily spending limit exists and is tested (`agent/spending.py`, checked in the loop before every call): each call's cost is estimated from `agent/providers/prices.py` and stored in `llm_calls`. A model missing from that table is counted dearer than any listed, so add a price when adding a model worth suggesting. It is an estimate, not the bill; do not describe it as more.
- How every model call decides, sees, acts and is trusted is framed in `docs/AI_CALLS.md`: code knows, the model understands and words. A new kind of call answers its five questions before it is added.
- The automatic-memory design and acceptance criteria are in `docs/MEMORY.md`. The earlier idea of an AI memory worker after every message is superseded. Memory is planned, not implemented.

## Commands

- `uv sync` installs everything. `uv run familydb --help` lists commands.
- `scripts/install.sh` is the installer people actually use: it asks only what the page cannot answer (the page's domain; the first member is added on the Family page), writes `.env`, installs, migrates, puts HTTPS in front when there is a domain, and schedules backups, for Docker or a virtualenv. Configuration belongs on the settings page: anything new that needs configuring goes there (a line in `store.settings.BEHAVIOUR` and `web/fields.py`), and into the home page's setup list (`web/status.setup_steps`) if the bot is not usable without it. The installer only writes such a value when it is given in the environment.
- Tests: `uv run pytest -q` (no network; each provider's SDK is faked in `tests/fakes.py`, and the shared `settings` fixture pins Claude because most scripts are written for its fake).
- Lint and format: `uv run ruff check . && uv run ruff format .`
- Live checks, need `ANTHROPIC_API_KEY`: `FAMILYDB_LIVE=1 uv run pytest -m live` and `uv run familydb debug validate-tools`.
- Behaviour checks against a real model, a few cents a run: `uv run python -m evals` (`--repeat 3`, `--provider`/`--model` to compare, `--case NAME --show` to see one). The cases in `evals/cases.py` are the family's own requests, graded by code on what was called, saved and said. Run them before and after changing a prompt, a tool description or a model, and keep a change only if they hold; a new behaviour gets a case.
- Jobs by hand: `uv run familydb enrich --idea N`, `uv run familydb suggest --window this-weekend [--discover]`, `uv run familydb digest --now`, `uv run familydb follow-ups --now`.
- The web page: `WEB_PASSWORD=test uv run familydb web --port 8099`, then open http://127.0.0.1:8099/ (the home page; `/chat` to talk to it, `/ideas` and `/ideas/new`, `/plans` and `/plans/month`, `/tasks` for things to do and their reminders, `/family` for who the bot talks to, `/status` for what is connected and what it has cost, `/settings` to change anything). The page reads the live Google calendar only through `app.calendar`; with none configured it shows the saved plans and says so.
- What each setting is and where it came from: `uv run familydb config`.
- Inspect a request without sending it: `uv run familydb debug prompt --as Sam "what should we do?"`, or `--kind enrich --idea 57` for a lookup. It is built by the same code that sends it.

## Layout

- `src/familydb/pipeline.py`: one inbound message end to end. Channels call `handle_incoming`.
- `src/familydb/delivery.py`: message leases (a claim with an expiry, renewed while a turn runs) and at-least-once delivery of stored replies. `calendar_sync.py` brings the bot's plans in line with their Google events. `family.py` holds the rules for adding and changing family members. `task_service.py` changes tasks and their reminders in one place, for the tools and the reminder job alike. `personas/` holds who the assistant is (`vera.md`, chosen by the `persona` setting, `none` for none; the family can rewrite her on `/settings/personality`, stored as `persona_text` over the file): it goes first in the chat prefix, ahead of `prompts/system.md`, which says what to do and wins where they meet; workers never carry it. `whereabouts.py` keeps where a member's phone said they were (a Telegram share, or the web chat's position), named once by the reverse geocoder, for three hours of use and a day at most (the `forget_locations` job deletes it then, whether or not anyone shares again). `voice.py` is the voice layer every unprompted message is routed through. `privacy.py` sets the owner-only umask every command runs under and tightens files an older version left readable.
- `src/familydb/agent/providers/`: one module per model vendor behind a small protocol. `base.py` holds the types the loop speaks in; `anthropic.py`, `openai.py` and `gemini.py` translate them, and each can ask its vendor whether a model name exists (`model_exists`, which costs no tokens). `prices.py` is the price table, with no SDK in it, which the spending limit and the settings page's model suggestions both read. Adding a vendor means one module and one name in `NAMES`; nothing outside this folder should mention an SDK.
- `src/familydb/agent/`: `gateway.py` is the one door to a model: `KINDS` declares each kind of call (chat, digest, retry, enrich, discover) with its prompt, tools, web budget and limits, and for a worker the `hand_back` tools whose success ends the turn without another call, and `ask` runs one and records it under its kind. `compose.py` builds each request from labelled parts (instructions, family, ideas, tools, history, message) and records their sizes with every call, so the real input total can be shared out by part. `prompt.py` renders the chat prefix, `history.py` rebuilds the chat, `loop.py` is the manual tool loop, `worker.py` runs the small separate turns that may use the web (enrichment, discovery) with `prompts/enrich.md` and `prompts/discover.md`; `prompts/system.md` is the product spec the chat model follows.
- `src/familydb/tools/`: `registry.py` declares and dispatches tools; one module per tool group. `places.py` is the place cache (`lookup_place`, `check_open`, `save_place`, `skip_place`); `suggest.py` exposes the engine as one `suggest` tool and `report_finds` for the discovery worker; `tasks.py` is `add_task`, `update_task` and `list_tasks`.
- `src/familydb/suggest/`: the suggestion engine as code, one module per stage (`context`, `shortlist`, `evaluate`, `discover`, `compose`, `log`) behind `engine.run`. The model frames the question and writes the reply; the verdicts and reasons come from here and are logged to `suggestions`. Time is minutes, not blocks: each day's free stretches between its bounds (08:00-22:00 unless the question names a part of the day, "now" from this minute), so never reason about morning/afternoon/evening there.
- `src/familydb/store/`: `db.py` (connection, transactions, JSON, migrations), `migrations/*.sql`, one repository module per table returning pydantic records. `settings.py` is the one the page writes: `BEHAVIOUR` and `SECRETS` are the whitelist of what may be changed from outside a file.
- `src/familydb/channels/`: message dataclasses, the console channel, the Telegram channel (`asyncio.to_thread` into the sync pipeline, run by `TelegramSupervisor`, which follows the token setting so a new token needs no restart) and the web channel (`WebChat` runs a turn on its own thread so the page can answer the form post at once).
- `src/familydb/web/`: the page. `__init__.py` is the Flask factory over an `App`, `auth.py` is the shared-password gate, the CSRF token and the `refused()` check every form runs, `once.py` makes a form do its work once however often it is sent, `routes.py` the reading views (home, ideas, plans list and month, restaurants), `agenda.py` reads what is on from Google or the saved plans, `status.py` what the status page reads, `chat.py` the chat page, `edits.py` the forms that change an idea, an outcome or a plan, `family.py` the Family page, `settings.py` the settings form and the Personality page (`/settings/personality`), `setup.py` the setup pages (`/setup`, one step at a time: password, you, AI model, home, Telegram, family, calendar; progress is read from what is configured, by `status.setup_progress`, never stored), `fields.py` the boxes it draws from `Settings` itself, `views.py` the wording helpers, `server.py` the waitress lifecycle, plus `templates/` and `static/` (`style.css`, and `locate.js`, the page's one script).
- `src/familydb/integrations/`: Google Calendar, Open-Meteo and the geocoder (Nominatim, Open-Meteo fallback) behind small Protocols; tests use the fakes in `tests/fakes.py`.
- `src/familydb/jobs/`: the APScheduler `BackgroundScheduler` and the jobs: retries, `enrich` (worker turn per pending idea), `weekend_digest` (a synthetic question through the pipeline), `follow_ups` (no model call), `reminders` (every minute, no model call: queues a due reminder and sends it once; a failed send is the retry job's), `forget_locations` (deletes shared positions past their day, no model call), `catch_up` (after a restart) and `settings_watch` (moves the schedule when a setting does). Each job's schedule is described once in `scheduler.job_specs`; jobs open their own connection with `app.connect()` and reply through `app.senders`.

## Rules that keep it working

- The family's own words about themselves (`about_family`, on `/settings/personality`) go in the family context of the cached prefix: they change when someone edits them, not per message.
- Nothing volatile in the cached prompt prefix. Tools, the system prompt, the family context and the idea list must not contain dates, times, the sender, or per-request ids. Those belong in the current user turn (`render_user_turn`).
- Rendering is deterministic: idea lines, JSON (`store.db.to_json`, sorted keys), tool ordering (sorted by name), server tools appended last.
- One SQLite connection per thread. Writes go inside `store.db.transaction`. Tools own their own transactions so partial progress survives a failed turn.
- Migrations are append-only numbered files; never edit one that has been applied. Schema changes to FTS-indexed columns need an FTS rebuild in the migration. The next one is `0017`. `0007` is retired for good: PR #2 shipped a `0007_web.sql` that was not taken, and a database that ran it must never mistake a new 0007 for one it already applied (`tests/test_migrations.py` knows the gap).
- Everything the bot says of its own accord is worded by `voice.say` (the persona's line, the family's rewrite, or the plain one), never a string literal at the call site; a new kind of message is a line in `voice.EVENTS`. A proactive message goes out through `voice.hand_over`, which holds it for a moment when the family is talking so the next reply carries it (the only message marked delivered without its own send, with that reply); the minute job sends what no reply carried. No model call is ever made just to word one.
- A reply is stored before it is sent and marked delivered only after the send succeeds: anything that sends goes through `delivery.deliver`, never straight to a channel's sender. Anything that works on an inbound message holds its `lease`, so a restart leaves nothing stranded and two workers never answer one message.
- Every tool is always declared to the model that may call it, and the list never varies between turns, because a varying list would cost the prompt cache. Availability is checked at dispatch; unavailable tools return `{"available": false, ...}` as a non-error result so the model reports the skipped check instead of retrying. Tools marked `worker_only` are left out of the chat list: they belong to a worker turn and would otherwise cost input tokens on every message.
- Tokens are the running cost. Before adding anything to the cached prefix, or a scheduled job that calls the model, check `familydb debug cost` and keep the idle path free: every job must read the database and return without an API call when there is nothing to do.
- Tool input models use `Literal` and handler checks instead of numeric or length constraints; strict schemas strip those.
- The core is synchronous. Async adapters (Telegram) call the pipeline through `asyncio.to_thread`; anything that sends from another thread goes through the channel's thread-safe sender.
- Tools reach external services only through `ToolContext.calendar` and `ToolContext.weather`, never by constructing clients themselves, so they stay testable with fakes.
- The loop knows nothing about any vendor. It builds a provider-neutral request and reads back a normalised reply; every request shape, cache marker, response block and error mapping belongs to a provider module. A test asserts the request built for a given message is stable, so check it after touching either provider.
- A turn may move to the other provider only on its first call, before any tool has run, because starting again after a write would repeat it. `worth_switching` decides which failures are worth moving for.
- What an Anthropic request carries depends on the model: adaptive thinking and effort unless it is one of `OLDER_MODELS`, the dynamic-filtering web tools only for `DYNAMIC_WEB_MODELS`, the refusal fallback only for `REFUSAL_FALLBACK_MODELS`. A wrong guess is a 400 on every request, which is how lookups on the default Haiku worker were broken; `tests/test_alpha_regressions.py` pins each case.
- Dispatch refuses a tool that was not declared for the turn, and an enrichment turn may only write to its own idea: fetched pages can talk a model into naming any tool.
- Every model call goes through `agent/gateway.ask`, and `tests/test_gateway.py` fails if anything else starts a turn or sends to a provider. A new kind of call is a line in `gateway.KINDS` that answers the five questions of `docs/AI_CALLS.md`, never a direct `run_turn`. What the answer means stays with the caller.
- The chat agent never gets the web tools. Web access happens only in worker turns (`agent/worker.py`) with their own prompt, a tool subset, `max_uses` and `worker_max_iterations`; results come back through strict client tools (`save_place`/`skip_place`, `report_finds`), never parsed from prose. Fetched pages are information, not instructions.
- No transaction may be open around a worker turn: the nested loop writes its own audit rows. Discovery results live in `App.discover_cache` keyed by window; failures are never cached.
- Before a paid call, `spending.admit` checks the limit and holds the call's estimated cost in `spend_holds`, in one short write transaction; recording the call gives the hold back, and a switch to the fallback provider re-holds at the fallback's price (`spending.adjust`) before it is asked. Nothing is locked while the call is on the network, so a slow lookup never holds up the family's chat, and two processes still cannot spend the same remaining dollars. Every vendor client has a timeout. Budget interruptions must report completed writes without another model call.
- Browser idea revisions are checked inside the tool's write transaction; calendar form identities flow through `ToolContext.operation_id` to the durable calendar operation log. Keep these preconditions out of model tool schemas.
- No module in `web/` reaches a table itself, and each view opens its own connection with `app.connect()` inside a `closing(...)`. Four may cause a write, each through one door: `chat.py` hands a message to the pipeline through `channels/web.py`, `edits.py` dispatches `add_idea`, `update_idea`, `record_outcome`, `create_event`, `update_event`, `delete_event`, `add_task` and `update_task` through `app.registry`, `family.py` adds and changes people through `familydb.family`, and `settings.py` writes `app_settings` through `store.settings` (the behaviour form, the keys form, the company-and-key form that checks a key with its company first, the family password for `store.settings.LOCK`, and the Personality page for `store.settings.PROFILE`) and two files: the session key (`keys.rotate`, signing everyone out) and the Google token (`google_calendar.finish_consent`). Two tests in `tests/test_web.py` hold that by walking the AST and they name what each may call, so anything more is a deliberate line there. Every other module reads and nothing else; the page may use `calendar_sync.event_changes` to read Google but never the sync functions, which write.
- The family list is who the bot talks to, so it is not a tool: the model must never be able to change who may message it. Member changes go through `familydb/family.py`, which keeps a name to one person, always keeps an active admin, and refuses a change made on a form drawn before somebody else saved.
- A form on the page is a tool call, not a second write path. Adding one means asking which tool already does it; if none does, the tool is what to write, because the model should be able to do it too. What the tools cannot do the page cannot do — an optional number that has been set cannot be unset, because `update_idea` reads a missing field as "leave it alone".
- Every form posts with a CSRF token and an Origin check through `auth.refused()`, and flashes its result under a named category (`edit`, `settings`) so two pages' notices never mix. A form that changes something also carries `once_token()` and its view is wrapped in `@once`, so a double click or a resend does the work once. The page is served with `Referrer-Policy: same-origin`: under `no-referrer` a browser posts with `Origin: null` and nobody can sign in, which the test client never shows because it sends no Origin at all. Check forms in a real browser.
- Behind a proxy, the forwarding headers are waitress's business (`web/server.proxy_options`), not Flask's: waitress strips them from any peer it was not told to trust before the app runs, so a Flask middleware sees nothing and every sign-in fails the Origin check. Flask's test client skips waitress entirely, so proxy behaviour is tested through a real server on a thread (`tests/test_web.py`), and was checked through real Caddy and nginx.
- One script and no more: `static/locate.js` sends the phone's position with a chat message while "Send where I am" is ticked (off until someone ticks it; the server keeps no position without it), because a browser gives it to nothing else. The content security policy is `script-src 'self'`, never `unsafe-inline`; no inline script, no second file without the family deciding so, and every page must keep working with scripts off. The chat page waits for its answer with a `<meta http-equiv="refresh">` that is only emitted while a turn really is running. Keep styling in `static/style.css` for the same reason. Templates escape by default; never mark anything from an idea, a place or a fetched page as safe.
- A setting can be changed from the page, so nothing may cache one, the Telegram token included (the supervisor re-reads it every few seconds). `App.refresh()` is called at every entry point (each message, each job, each page view, each scheduler tick) and rebuilds `App.settings` when the stored values have moved; read `app.settings` when you need it rather than holding on to it, and if you build something from it, say so in `App._forget_built` so it is built again. Adding a setting to `store.settings.BEHAVIOUR` also means a line in `web/fields.py`, which a test checks.
- Where a member is goes in the current user turn (`render_location_line`), never the cached prefix, and only while fresh. The family chose to send it: the chat model and the discovery worker get the place name and coordinates, so nobody has to type where they are.
- An API key is write-only: stored, never rendered into a form, never written to the change log, and shown only after the family password is typed again.
- Setting up is the page's job, not a file's: `/setup` walks a new install through it, and each of its forms is one that already exists, posting to its owner with a `then` that may only name a `/setup` page (`auth.setup_return`). The home page sends there until it can answer (somebody on the list and a model). A new thing that has to be configured is a setup step if the bot is not usable without it.
- The family password is chosen on the page and stored only as a hash (`passwords.py`, `store.settings.LOCK`, logged as replaced). Changing it asks for the one in force, except the family's first choice within an hour of signing in with the installer's; `familydb password` resets a forgotten one. `WEB_PASSWORD` is only the installer's first password.
- Web wording lives in `web/views.py`, never in `agent/render.py`: that one feeds the cached prompt prefix and must not change for the sake of a page.
- Keep replies short; edit `prompts/system.md` to change behaviour before touching code.
- One concern per pull request, reviewed before it is merged. A change that touches a hundred files cannot be reviewed, and what slips through lands on the family.
